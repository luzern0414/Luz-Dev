# Luz Dev 闭环结果页规范

状态：verified（Luz Dev 设计基线）
更新：2026-10-26

本规范回答一个业务动作得到结果后，用户应停留在哪里、返回到哪里，以及页面如何证明结果已经发生。所有 Luz Dev 项目在定义支付、表单提交、批量任务、预约、售后或状态操作时，都应使用这张决策表。

## 1. 不可绕过的事实规则

1. 服务端持久状态是唯一事实源。HTTP 200 只证明请求已处理，客户端支付 SDK 回执只触发查询，二者都不等于业务完成。
2. 页面落点由服务端结果契约中的 state、terminal、retryable 和 next_action 决定。
3. pending、processing、unknown 不得显示为成功或失败。
4. 结果页必须可刷新、可深链，并从服务端重建；不得依赖上一步页面的内存或客户端金额。
5. 重复点击、刷新、网络重试和渠道回调都必须幂等。
6. 成功后使用 replace 导航，Back 不得回到已提交表单、支付唤起页或重复提交入口。

## 2. 页面落点决策矩阵

| ID | 场景 | 结果落点 | 用户看到什么 | 禁止做法 |
|---|---|---|---|---|
| inline | 可逆、低风险、上下文稳定的即时修改 | 当前页就地更新 | 新值 + 短 Toast | 为保存标签或开关跳独立成功页 |
| form-error | 字段错误、可修正的业务拒绝 | 原表单 | 保存原输入、错误汇总、字段错误、聚焦第一处 | 清空输入或跳通用失败页 |
| result | 交易、申请、多步骤表单已经形成业务事实 | 独立结果页 | 业务编号、关键摘要、最终状态、唯一下一步 | 只显示 Toast 或客户端伪造金额 |
| processing | 异步任务尚未 terminal | 处理中页 | 当前阶段、进度、更新时间、稍后查看 | 显示假成功、无限转圈、无恢复路径 |
| partial | 同一批次部分成功、部分失败或跳过 | 汇总结果页 | 总数、成功、失败、跳过、失败明细 | 使用全成功视觉或笼统“操作失败” |
| failure | 已确认的终态失败，或提交后无法返回编辑上下文 | 失败结果页 | 安全原因、是否产生副作用、重试/详情/支持入口 | 暴露堆栈、内部路由、渠道报文 |

判断顺序：

1. 结果是 field/business validation 且用户可修正：原表单。
2. 结果是低风险即时更新且上下文连续：当前页。
3. 结果仍是处理中或 unknown：处理中/确认中页。
4. 批次同时存在成功和失败：部分成功汇总页。
5. 已形成业务编号或完成交易：结果页；失败时使用失败结果页。

## 3. 结果契约

推荐 API envelope：

| 字段 | 类型 | 含义 |
|---|---|---|
| state | enum | success、processing、partial、failed、cancelled、unknown |
| terminal | boolean | 是否已有可信终态 |
| operation_id / flow_id | opaque string | 结果页刷新和恢复所用标识 |
| business_ref | string | 订单、支付、预约、申请或批次编号 |
| retryable | boolean | 是否允许用户安全重试 |
| next_action | enum | view_order、view_detail、retry_payment、resume_form、retry_failed_items、contact_support、none |
| support_ref | string/null | 支持人员定位问题所需的非敏感编号或 trace_id |
| summary | object | 服务端生成的脱敏摘要，如金额、时间、状态 |

前端只渲染服务端允许展示的 summary 字段。URL 只放 opaque flow token 或非敏感业务 ID；不放手机号、地址、支付签名、渠道原始报文或金额明细。

## 4. 支付结果

路由样例：

- 小程序/App：`/pages/result/payment?flow={token}`
- Admin：`/payments/{payment_id}/result` 或订单详情内的支付结果区域
- 事实接口：`GET /api/v1/app/payments/{payment_id}`

支付 SDK 返回后必须执行：

1. 使用 replace 进入“正在确认支付”页面。
2. 查询服务端支付状态。
3. 若 status=success，且金额、业务单与归属核对通过，显示“支付成功”。
4. 若 status=failed/closed 且 terminal=true，显示“支付未完成”或“支付已关闭”，按 retryable 提供动作。
5. 若 status=processing/pending，继续按 1、2、4、6、8 秒轮询。
6. 达到轮询上限仍 unknown 时，显示“支付结果确认中”，明确“请勿重复支付”，提供手动刷新与查看订单。
7. 页面隐藏时暂停轮询，重新可见或回前台时恢复。

支付成功页内容：

- 标题“支付成功”，图标作为辅助，状态文字同时可读。
- 服务端金额、订单/支付编号、支付方式、完成时间。
- 主动作“查看订单或订单详情”。
- 次动作“继续购物”，由业务决定。
- 不展示渠道签名、商户号、原始回调或客户端回传金额。

支付失败或取消：

- 用户取消：标题“支付未完成”或“已取消支付”；说明本次支付未完成，不得断言未扣款，除非服务端确认。
- 渠道拒绝：使用安全原因和 retryable；可重试时主动作“重新支付”。
- 金额/业务单不符：显示受控安全提示和支持编号，不自动重试。
- 已取消订单收到迟到支付回调：保留支付事实，进入人工退款/处理语义；不得倒回订单成功。

## 5. 表单结果

| 表单类型 | 成功返回 | 失败返回 |
|---|---|---|
| 编辑已有资料 | 原页，就地更新并 Toast | 原页，保留输入 |
| 新建实体/申请/报名/售后 | replace 到结果页，展示编号、摘要和下一步 | 可修正错误回原表单；终态拒绝进失败页 |
| 多步骤向导 | replace 到结果页，Back 不回已填写向导 | 保持当前步骤和全部输入，聚焦错误 |
| 短表单且无业务凭证 | 关闭居中面板或留在原页，更新列表并 Toast | 原面板 / 原页，保留输入 |

结果页显示的编号表示“已提交/已创建”，不能自动解释为审批通过、履约完成或退款到账。审批类业务应显示明确状态，如“申请已提交，等待审核”。

## 6. 异步任务与部分成功

异步任务返回 202 或 processing 时，进入处理中页并展示：

- 当前阶段和已完成数量。
- 最后一次更新时间。
- 离开页面后仍可从“任务中心/详情”继续查看。
- terminal=true 后显示成功、部分成功、失败或取消。

批量操作不得吞掉单条错误。汇总页必须满足：

`total = success + failed + skipped`

失败项提供下载和“仅重试失败项”。重试沿用原批次和项目标识，避免成功项被重复执行。

## 7. 失败页与恢复

失败页必须回答三个问题：

1. 发生了什么：使用用户语言和安全错误码，不展示原始异常。
2. 是否有副作用：例如是否已扣款、库存是否已占用、申请是否已受理；无法确认时使用“结果确认中”。
3. 用户能做什么：由 next_action 提供重试、返回修改、查看详情或联系支持。

权限失败、会话过期和网络中断不应一律进入失败结果页：

- 会话过期：重新认证后安全回跳当前结果页。
- 403：说明权限不足，提供返回安全入口；不暴露对象是否存在。
- 网络未知：保留当前上下文并可安全重试查询，不认定业务失败。

## 8. 文案、视觉与埋点

- 结果页的标题、文案、图标、插画、动作数量与“完成”去向按 Luz System 界面通用规范（`references/ui-standards.html` 的操作反馈与结果页）实现，本篇不另定。
- 实现侧要求：状态同时用标题与读屏文本（aria-live）表达，不只靠颜色；处理中提供“稍后查看”，不让用户固定在页面等待；尊重 reduced-motion。
- 关键结果页记录进入事件、终态变化、轮询超时、重试动作和支持编号。

## 9. 测试清单

- 支付 SDK 成功但服务端 pending；SDK 取消但回调最终成功。
- 支付回调重复、迟到、金额不符、订单已取消。
- 页面刷新、前后台切换、轮询超时、重新进入结果页。
- 表单校验失败保留全部输入；成功后重复点击不重复创建。
- 结果页越权、会话过期和安全回跳。
- 异步任务 progress 不倒退、terminal 后才显示结果。
- 部分成功统计一致、失败项下载和仅重试失败项。
- failure、unknown、cancelled 的视觉与文案不混淆。
