# 配置文件与日志

后端的运行配置与日志怎么写、怎么查、存多久。运行参数写在代码仓库的配置文件里，服务端热加载，不在后台展示（用户 2026-10-29 决定）；日志一行一条 JSON，能按请求串起来，不含秘密与多余的个人信息，按法定期限集中留存。哪些参数要可配置、客户端怎么拉取与兜底，见 Luz System `references/config-design.html`；部署、监控与告警阈值见 `operations.md`；审计记录的表结构见模块详设 foundation，运行配置的接口与表见模块详设 config。相关规范：OPS-005、CONF-*、SECRET-*、OBS-*、AGENT-018。

## 1. 五类设置分开放

| 类别 | 例子 | 放在哪 | 谁改 | 怎么生效 |
|---|---|---|---|---|
| 秘密 | AppSecret、商户私钥、APIv3 密钥、数据库口令、签名密钥、字段加密密钥 | 密钥服务或服务器受限文件（`/etc/luz/secrets/`，compose secrets 挂载），由代码按文件读取 | 运维 | 轮换流程，新旧并存一段时间（SECRET-001、SECRET-002） |
| 部署参数 | 数据库与 Redis 地址、端口、进程数、连接池、可信代理网段、服务名 | 环境变量（`/etc/luz/api.env`，模板 `assets/deploy/api.env.example`） | 运维 | 重启 |
| 运行参数与开关 | 上传上限、超时与重试、轮询间隔、限流阈值、功能开关、最低可用版本、智能体上限、日志级别 | 代码仓库 `config/runtime/*.toml` + 字段说明 | 开发，经代码评审 | 服务端热加载（本篇 §2） |
| 经营与运营内容 | 门店营业时间、公告、横幅、券、奖品；经营规则：退款手续费、储值扣减顺序、退券策略、补卡费、起送价、配送费、包装费 | 数据库：经营规则在“经营设置”（模块详设 business，`business_settings`，键由业务模块用 `luzback.business` 登记），其余在各业务模块 | 运营，在后台 | 即时，写审计；影响资金的经营设置要求重新验证身份（ADMIN-006） |
| 前台文案与展示 | 小程序上的提示、空状态、须知、规则说明、弹窗文字；首页模块顺序与显隐、展示开关 | 数据库（模块详设 content：`ui_texts`、`display_settings`）；`admin_visible` 为否的项（通用控件词、系统级提示、法规固定文字、技术性展示配置）存在后端但不在后台展示 | 后台可见的由运营在“文案与展示”页改；隐藏的由开发经文案种子与迁移改 | 保存即生效，小程序下次显示该页时更新（MP-006、ADMIN-005） |

运行参数不在后台展示，也不做配置中心页面，除非用户另行要求（用户 2026-10-29 决定）。前台的文字提示与展示配置尽量由后端下发、后台实时维护，不写死在小程序里；需要存在后端但不必给运营看的项标 `admin_visible` 为否（用户 2026-10-29 要求）。分不清时问：这个值要不要商户日常自己改？要，就是经营内容（经营规则进“经营设置”）或文案与展示，进后台；只在排障或调优时改，就是运行参数，进配置文件。例如退款手续费、储值扣减顺序、退券策略、补卡费是经营规则（2026-10-30 用户决定从配置文件挪到后台）；接口超时、限流阈值是运行参数。

## 2. 运行配置文件

### 2.1 目录与格式

```text
config/runtime/
  base.toml        # 全部键与默认值，每个键上方一行注释：用途、单位、范围
  dev.toml         # 只写与 base 不同的值
  staging.toml
  prod.toml
backend/.../runtime_config.py   # 字段说明：Pydantic 模型，唯一的类型、范围与元数据来源
```

- 格式用 TOML：支持注释，同一个键重复定义是错误，没有 YAML 的隐式类型陷阱。只放纯数据，不加模板、变量插值或条件；需要按环境区分就写进环境文件。
- 只设 dev、staging、prod 三个环境文件，不按功能或客户再拆；门店、渠道、客户端版本的差异写成文件内的覆盖规则（§2.6）。
- 键名小写蛇形，按分组成表：`[upload]`、`[http]`、`[jobs]`、`[agent]`、`[client]`、`[features]`；单位写进键名：`timeout_ms`、`max_mb`、`interval_s`。
- 命名实体用表键（`[http.wechat]`），不用带 `name` 字段的数组，覆盖时才能按键合并。

### 2.2 字段说明

每个键在 Pydantic 模型里登记，元数据放在 `Field(json_schema_extra=...)`：

| 项 | 内容 |
|---|---|
| 类型与默认值 | 默认值本身也要通过校验；必填项越少越好，默认值选安全的一侧（新功能开关默认关） |
| 范围与单位 | `ge`/`le`、枚举、正则；单位与键名一致 |
| 作用范围 | 全局、门店、渠道、客户端版本；只允许登记过的范围写覆盖 |
| 能否热加载 | `reloadable`：超时、重试、限流、开关、名单、文案、日志级别可以；端口、进程与并发数、连接池、数据库与存储地址不可以 |
| 下发客户端 | `client_visible`，默认否；只有标了的键进 `/api/v1/app/config` |
| 风险与负责人 | `risk`：低、高（支付、上传上限、维护模式、限流）；负责人写模块名 |

跨字段约束（最小值不大于最大值、开关打开时依赖的键必填）写成模型级校验器。CI 把三个环境文件各加载一遍，字段说明与 `base.toml` 不一致（缺键、多键）直接失败。

### 2.3 加载顺序

代码默认值 < `base.toml` < `<环境>.toml` < 文件内覆盖规则（按请求的门店、渠道、客户端版本命中）。环境变量只给部署参数用，不覆盖运行参数，避免同一个值有两个来源。Pydantic 会静默忽略拼错的环境变量名，启动时另扫一遍 `LUZ_` 前缀，不认识的变量名打警告日志。

### 2.4 校验与失败处理

- 结构与语义两步校验：先解析与类型，再范围、跨字段与引用（引用的文件存在、名单里的门店存在）。
- 文件里出现未登记的键一律报错，不忽略：拼错的键会让默认值悄悄生效。
- 启动时校验失败：逐条打印“键、当前值（秘密打码）、原因、允许范围”，进程非零退出，编排不会把它标为就绪。
- 热加载时校验失败：拒绝整份新文件，继续用旧配置，写 `config.reload_rejected` 错误日志、`luz_config_reload_failures_total` 加一并告警；修好文件后再加载。

### 2.5 热加载

- 触发：`watchfiles` 监听整个配置目录（不是单个文件，编辑器保存常是先写临时文件再改名），防抖 1–2 秒（骨架默认 1.5 秒）；文件系统通知不可用时用轮询；另有内部 `POST /internal/config/reload`（只对内网开放并校验运维令牌，发布脚本同步完文件后调用）。
- 原子替换：在旁路把合并后的配置整份解析、校验成一个不可变快照，通过后一次性替换引用。禁止逐键修改或原地重新初始化（会出现半新半旧）。加载过程用一把锁串行，读取不加锁。
- 请求内一致：每个请求、任务或智能体运行开始时取一次快照，全程用这一份；结算、支付与进行中的长任务不受中途变化影响。
- 不能热加载的键：变化时不应用，写警告日志并在 `/internal/config` 列为“待重启生效”，下次滚动重启生效。
- 多进程与多实例：每个进程各自监听并加载；每个实例在指标 `luz_config_info{version}`、`/internal/config` 与每条日志里带当前配置版本，版本不一致超过 5 分钟告警。
- 容器编排：配置目录整体挂载才会自动更新；以子路径挂载或注入成环境变量的不会更新，只能滚动重启；挂载更新有延迟，以实例上报的版本为准。

### 2.6 版本、灰度与回滚

- 配置版本：合并后的规范化内容取摘要（SHA-256）的前 12 位；`config_loads` 记录每个实例每次加载的版本、来源提交、结果与变化的键（模块详设 config）。
- 变更走代码评审：提交说明写原因；高风险键要第二人评审；“改了什么”看提交，“何时生效”看加载记录，两者都要有。
- 灰度：在环境文件里写覆盖规则（门店名单、渠道、客户端版本区间、用户分桶百分比，同一用户稳定落在同一桶）；观察错误率与关键指标后改成全量并删除覆盖。不一次性全量推送影响支付、上传或限流的改动。
- 回滚：还原配置文件的提交并同步，服务端热加载；配置不引用会在外部变化的资源，回滚才可靠。
- 临时的发布开关全量后按期删除，键和判断代码一起删。

### 2.7 客户端下发

- 只下发 `client_visible` 的键（白名单），按端与客户端版本过滤，新键只给认识它的版本；不下发秘密、内部地址与服务端专用键。
- 响应带 `config_version`（也作 `ETag`），版本未变返回 304；客户端在后续请求头带当前版本，便于排查。
- 客户端每次读取都要有默认值；拉取失败、值非法或类型不对时用上次有效值，再不行用安装包默认值，不报错、不挡住使用（Luz System 远程配置规范）。

### 2.8 秘密不进配置

- 秘密不进配置文件、仓库、镜像（`ENV`/`ARG`）与前端包；仓库只有带占位的示例文件；提交前与 CI 都做秘密扫描。
- 优先由编排挂载成文件读取（环境变量可能出现在进程信息、崩溃转储与日志里）；读入后用 `SecretStr` 一类类型，打印、报错与 `/internal/config` 一律打码。
- 泄露处置顺序：吊销、轮换、清除出现过的地方（日志、提交历史、截图）。

### 2.9 硬性规定

| 事故类型 | 规定 |
|---|---|
| 写错的文件在线上生效 | 先整份校验再替换；失败保留旧配置并告警 |
| 拼错的键让默认值悄悄生效 | 未登记的键报错；环境变量前缀另扫 |
| 单位理解错（秒当毫秒） | 单位写进键名，字段说明写范围 |
| 半新半旧 | 只做整份快照替换，请求开始取一次 |
| 以为改了就生效 | 以实例上报的版本为准；不能热加载的键明确列出 |
| 一次性全量出事 | 高风险键先覆盖一部分门店或用户，再全量 |
| 重载接口被外部调用 | 只对内网开放并校验令牌 |
| 热加载时文件读不全或同步到一半 | 按校验失败处理，保留旧快照；同步先写临时文件再改名 |
| 客户端拉不到配置就不能用 | 客户端用缓存与安装包默认值照常使用 |

## 3. 日志

### 3.1 分类与去向

运行、访问、安全与审计的用途不同，分开存放；每个项目在方案里写一张日志清单：各类记什么、存在哪、谁能看、存多久。

| 类别 | 记什么 | 写到哪 | 谁能看 | 留存 |
|---|---|---|---|---|
| 运行日志 | 启动与关闭、依赖调用失败、异常、任务运行、配置加载 | stdout → 采集器 → 日志平台 | 开发、运维 | 热存 30 天，归档到 6 个月 |
| 访问日志 | 网关每个请求一行（nginx JSON）；应用每个请求一条汇总行 | stdout → 日志平台 | 运维、安全 | 6 个月 |
| 安全事件 | 登录失败与锁定、越权、令牌异常、验签失败、限流命中、输入校验异常激增、管理员敏感操作 | stdout，按 `category=security` 单独成流并告警 | 安全、运维 | 6 个月 |
| 审计记录 | 后台写操作、权限变更、导出、退款与改价、查看敏感明文 | 数据库 `audit_logs`，与业务同事务写入；应用账号只有插入权限（OBS-002） | 审计员只读，后台审计页 | 建议 1 年，见 §3.9 |
| 业务状态流水 | 订单、支付、退款、核销的状态变化 | 业务库的状态流水表，不是日志文件 | 客服、运营（后台详情页） | 与订单相同 |
| 智能体运行 | 每次运行一条 trace，步骤、耗时、token、工具与结果；默认不记原文 | trace 与运行日志 | 开发 | 6 个月（OBS-004） |

运行参数的变更不进审计表：改了什么看配置文件的提交，何时生效看 `config_loads` 与 `config.reloaded` 日志（§2.6）。经营设置、前台文案与展示的修改在后台发生，写审计记录与 `content_revisions`（OBS-002）。

### 3.2 级别

| 级别 | 用在 | 例子 |
|---|---|---|
| `DEBUG` | 诊断细节；生产默认关闭，排障时按模块临时打开并自动恢复 | 计价中间值、外部接口的请求摘要 |
| `INFO` | 按预期发生的业务事件与汇总 | 下单成功、请求汇总行、任务完成、配置加载 |
| `WARNING` | 意外但仍能继续，或预期内的业务失败 | 库存不足、验证码错误、重试后成功、降级、要重启才生效的配置 |
| `ERROR` | 本次功能没能完成，需要有人看 | 未处理异常、外部依赖重试用尽、发件箱进死信 |
| `CRITICAL` | 资金或数据可能出错，或服务无法继续 | 回调金额与订单不符、对账差异、审计写入失败、启动配置校验失败 |

- 生产默认 `INFO`；日志级别是可热加载的运行参数（`[logging] level`、按模块覆盖）。
- 用户输入错误、余额不足这类预期内失败不记 `ERROR`，否则告警会被淹没；记 `WARNING` 或 `INFO` 并带 `reason`。
- 同一个异常只在请求边界或全局异常处理里记一次并带堆栈；中间层要么处理，要么包装后上抛，不各打一遍，也不吞掉不记。

### 3.3 字段

一行一条 JSON，字段名全项目统一（参照 OpenTelemetry 日志数据模型与 Elastic 通用字段）：

| 字段 | 内容 |
|---|---|
| `ts` | UTC，ISO 8601，毫秒，结尾 `Z` |
| `level`、`logger` | 级别；按模块命名的 logger（`__name__`） |
| `service`、`env`、`version`、`instance`、`config_version` | 服务名、环境、发布版本、实例、当前配置版本 |
| `event`、`message` | 事件名（§3.4）；给人读的一句话，模板固定不拼用户输入 |
| `trace_id`、`span_id`、`request_id` | 链路与请求编号（§3.6），小写十六进制 |
| `user_ref`、`store_id` | 用户内部编号（不用手机号、openid 原值）；门店 |
| `http.method`、`http.route`、`http.status`、`duration_ms` | 请求汇总行必带；`http.route` 用路由模板（`/orders/{id}`），不用实际路径 |
| `outcome`、`reason` | `success`、`failure`、`unknown`；失败原因用稳定的小写代码 |
| `error.type`、`error.message`、`error.stack` | 异常类型、脱敏后的消息、截断到 2000 字的堆栈 |
| 业务编号 | `order_no`、`payment_no`、`job`、`run_id` 等，按事件需要 |

每个请求在结束时写一条汇总行（`http.request`）：路由、状态、耗时、用户与门店、数据库与外部调用次数及耗时、结果；排障先看这一行，再按 `trace_id` 展开。

### 3.4 事件名与写法

- 事件名用小写 `领域.动作`：`order.created`、`payment.notify_verified`、`refund.failed`、`config.reloaded`、`job.finished`；结果放 `outcome`，不另造 `_success`/`_fail` 两个名字。
- 安全事件用 `security.` 前缀加 OWASP 日志词汇表的名称：`security.authn_login_fail`、`security.authz_fail`、`security.input_validation_fail`、`security.session_token_reuse`，便于安全工具识别。
- 事件名在代码里集中登记成常量，新增要评审；不在日志调用处临时起名。
- 用框架的 `log_event(logger, "order.created", order_no=..., amount_cents=...)` 传结构化字段，不把变量拼进消息字符串；不直接把整个对象序列化进日志。

### 3.5 不能记的内容与脱敏

| 内容 | 处理 |
|---|---|
| 口令、访问与刷新令牌、签名、验证码、API 密钥、数据库连接串、会话标识 | 一律不记；会话标识需要关联时只记哈希前 8 位 |
| 支付私钥、APIv3 密钥、回调明文、银行卡号、安全码、有效期 | 一律不记；卡号最多后 4 位 |
| 手机号 | `138****1234` |
| 证件号 | 只留前 6 后 4 或只留后 4 |
| openid、unionid | 哈希后记录 |
| 人脸、精确位置、健康等敏感个人信息 | 不记 |
| 请求体、响应体 | 默认不记；需要时只记白名单字段 |

- 在格式化器之前统一脱敏：字段名黑名单（`password`、`token`、`secret`、`authorization`、`cookie`、`sign`、`card` 等）加正则兜底；框架的 `redact` 已处理手机号、令牌与证件号，项目按需扩充。
- 防日志注入：只用 JSON 输出；转义回车、换行与控制字符；用户输入的字段截断到 512 字；消息模板保持常量。
- 链路传播头（`traceparent`、`baggage`）里不放任何个人信息或凭据。
- 返回给前端的错误不带堆栈与内部信息，只给稳定错误码与 `request_id`。

### 3.6 关联与追踪

- 请求入口：收到合法的 W3C `traceparent` 就沿用其 trace，否则新建；外部公网请求的采样标志不盲从。没有链路追踪的项目至少生成 `request_id` 与 `trace_id`（框架当前用 `X-Request-Id`、`X-Trace-Id`）。
- 上下文用 `contextvars` 保存，由日志过滤器注入每条日志；线程与 `asyncio` 都适用。
- 响应头与错误响应都返回 `X-Request-Id`；前端错误页显示它，用户报障时复制给客服（OBS-001）。
- 向下游 HTTP、消息队列、发件箱事件写入 `traceparent`，消费端取出后继续同一 trace；定时任务每次运行新建 trace，并记 `job` 与 `run_id`。
- 智能体：每次运行一条 trace，日志带 `request_id`、`run_id`、`trace_id`（AGENT-018）。

### 3.7 性能与可靠性

- 日志不能让业务失败：日志调用本身的异常吞掉并计数；生产设 `logging.raiseExceptions = False`。
- 不阻塞事件循环：写 stdout 用队列（`QueueHandler` + `QueueListener`），队列设上限，满了丢 `DEBUG` 与 `INFO` 并计 `luz_log_dropped_total`；`WARNING` 以上、安全事件不丢；审计记录走数据库，不走日志通道。
- 昂贵的参数先判断 `logger.isEnabledFor(level)`。
- 采样只用于高频且成功的 `INFO`（健康检查、轮询），按 `trace_id` 决定，同一请求要么全留要么全丢；错误、警告、安全与审计不采样。
- 库代码只 `getLogger(__name__)`，不加处理器、不改根 logger；不在每个请求或对象上新建 logger；生产不用 `print`，不直接输出 traceback。
- 合规必需的日志（访问、安全、审计）不能被配置整体关闭。

### 3.8 存储与轮转

- 应用只写 stdout，由运行环境收集；容器内不写日志文件。
- Docker 的 `json-file` 默认不轮转：每个服务都设 `max-size` 与 `max-file`（运维套件已设：api 50m×5、nginx 100m×10）；本地文件只是缓冲，不是留存。
- 采集器（Grafana Alloy 或 Fluent Bit）把日志送到集中存储（Loki、阿里云日志服务或同类）；索引标签只用低基数字段（服务、环境、级别、类别），`trace_id`、订单号、用户编号不做标签。
- 热存 30 天供检索，之后转低频或归档存储直到期满；归档附内容哈希，存储开启版本或对象锁；到期自动删除，删除任务写运行日志。
- 只存在一台机器上、没有备份的日志不算留存。

### 3.9 留存期限

期限从记录产生（交易类从交易完成）起算；到期删除或匿名化，法定期限未满时只存储与保护，不做其他处理。期限写进技术方案的上线章节。

| 类别 | 最低留存 | 依据 | 性质 |
|---|---|---|---|
| 网络与访问日志（网关访问、应用请求、运行日志） | 6 个月 | 《网络安全法》第二十三条（2025 年修正，2026-01-01 施行；原第二十一条，内容未变） | 法定 |
| 安全事件日志（登录失败与锁定、越权、验签失败、限流命中、异常管理操作） | 6 个月；事件处置记录建议 3 年 | 同上；《数据安全法》第二十九条 | 法定加推荐 |
| 审计记录（后台写操作、权限、导出、配置变更、查看敏感明文） | 建议 1 年；涉及个人信息的批量导出与越权操作建议 3 年 | GB/T 22239-2019 安全审计；GB/T 35273-2020 第 7.1、11.7 条 | 推荐（等保测评要求“符合法律法规要求”） |
| 个人信息处理记录（影响评估报告、委托处理与对外提供台账） | 3 年 | 《个人信息保护法》第五十六条；《网络数据安全管理条例》第十二条 | 法定 |
| 交易与订单（含支付、物流、售后信息） | 3 年（平台经营者法定；单店小程序建议同样执行） | 《电子商务法》第三十一条；《网络交易监督管理办法》第三十一条 | 平台法定 |
| 支付流水与对账 | 建议 5 年；作为会计凭证或对账依据导出归档的部分按会计档案期限（凭证与账簿 30 年，银行对账单 10 年） | 《非银行支付机构监督管理条例实施细则》第六十一条（义务在支付机构）；《会计档案管理办法》附表 | 推荐；会计部分法定 |
| 智能体与生成内容日志（运行记录、标识与提供对象） | 6 个月 | 《互联网信息服务算法推荐管理规定》第二十八条；《人工智能生成合成内容标识办法》第九条 | 面向公众提供时法定 |

- 单店小程序是否属于“平台经营者”是法律判断，Luz Dev 不替商户下结论：默认按 3 年执行，写进方案请商户确认。
- 应用日志里不放完整交易明细；交易与订单以数据库记录为准，日志只放编号与状态，二者各按各的期限。
- 《生成式人工智能服务管理暂行办法》第十一条要求不得非法留存能识别使用者身份的输入信息与使用记录：智能体日志默认不记原文（AGENT-018）。

### 3.10 日志本身也是个人信息

带用户标识的操作记录属于个人信息（GB/T 35273-2020 附录把日志里的操作记录列为个人上网记录），按个人信息处理：

- 最小化：只记排障与审计必需的字段（《个人信息保护法》第十九条）。
- 去标识化与加密：手机号、证件号脱敏，用户用内部编号；敏感个人信息不进日志（第五十一条）。
- 访问控制：日志平台按角色授权，系统、安全与审计管理员分开；导出日志要审批并写审计；查看审计记录本身也写审计。
- 防篡改与备份：审计与安全日志集中存放，只追加，开启对象锁或只读；定期备份（GB/T 22239-2019 安全审计 c、d 项）。
- 到期删除：按 §3.9 自动清理，清理任务本身写运行日志。
- 银行卡号、安全码、有效期不得出现在任何日志里（《银行卡收单业务管理办法》第二十八条）。

### 3.11 告警

错误率、延迟与饱和度用指标计算并告警（operations.md §4，99.9% 燃烧率 1h/5m 14.4 倍、6h/30m 6 倍呼叫值班，3d/6h 1 倍开工单）；日志负责定位，以及下面这些只在日志里看得到的情况：

| 触发 | 级别 |
|---|---|
| 任何一条 `CRITICAL`（金额不符、对账差异、审计写入失败） | 立即呼叫 |
| `security.*` 突增：登录失败、越权、验签失败超过基线 | 呼叫或群消息 |
| `config.reload_rejected`，或各实例配置版本不一致超过 5 分钟 | 群消息 |
| 某服务连续 10 分钟没有任何日志（采集中断或进程卡死） | 群消息 |
| `luz_log_dropped_total` 大于 0 | 工单 |

每条告警写明负责人与处理手册；告不出行动的规则删掉，误报多会淹没真告警。

### 3.12 硬性禁止

1. 记录口令、令牌、密钥、完整证件号与银行卡号、会话标识、完整请求体。
2. 把用户输入拼进消息模板；输出非 JSON 的多行日志。
3. 同一异常在多层重复打印，或吞掉异常不记。
4. 预期内的业务失败记 `ERROR`。
5. 日志失败导致请求失败，或同步写网络阻塞事件循环。
6. 审计记录与运行日志混存，或应用账号能改删审计记录。
7. 对外返回堆栈或内部错误信息。
8. Docker 不设轮转；高基数值做索引标签。
9. 日志只存本地、没有集中留存与备份；合规日志可以被整体关闭。
10. 在 `traceparent`、`baggage` 里放个人信息。
