# 高并发抢购与热点库存（秒杀、限量、抢课）

普通门店与中小电商用 inventory.md 的条件更新就够了。只有当同一 SKU 在短时间内收到远超库存的请求时，才按本文分层削峰。
相关规范：ABUSE-001、ORDER-002、ORDER-003、MKT-003。

## 1. 分层削峰

| 层 | 做法 | 目的 |
|---|---|---|
| 页面 | 静态化、CDN、按钮在开始前不可点、提交后禁用 | 挡住重复点击与刷新 |
| 入口 | 按用户 / 设备 / IP 限流；验证码或答题；活动开始前发放令牌，令牌数 ≈ 库存 × 系数 | 过滤脚本与无效请求 |
| 资格 | 一人一单：Redis `SADD` 或数据库唯一约束（活动 ID + 用户） | 防重复购买 |
| 预扣 | Redis Lua 原子预扣（下方脚本），返回 0 直接告知售罄 | 绝大多数请求不进数据库 |
| 下单 | 预扣成功的请求进入队列异步下单，或同步进入数据库条件扣减 | 数据库只承受 ≈ 库存数的写 |
| 兜底 | 数据库条件更新仍然执行；数据库失败时回补 Redis | Redis 与数据库最终一致，不超卖 |

```lua
-- KEYS[1] = stock:{sku}  KEYS[2] = buyers:{activity}  ARGV[1] = qty  ARGV[2] = user_id
if redis.call('SISMEMBER', KEYS[2], ARGV[2]) == 1 then return -1 end   -- 已购买
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock < tonumber(ARGV[1]) then return 0 end                         -- 售罄
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('SADD', KEYS[2], ARGV[2])
return 1
```

## 2. 一致性

| 问题 | 处理 |
|---|---|
| Redis 预扣成功、数据库扣减失败 | 回补 Redis（`INCRBY` + `SREM`），记录日志 |
| 下单后未支付 | 预占过期释放：数据库回补后同步回补 Redis |
| Redis 宕机或数据丢失 | 活动暂停；以数据库为准重建 Redis 库存 |
| 活动结束 | 对账：数据库已售 + 剩余 = 活动库存；Redis 只做缓存 |

## 3. 热点行

- 同一行被大量并发更新时，数据库行锁排队会拖慢整体：拆分库存桶（同一 SKU 拆为 N 行，随机选桶扣减，汇总展示），或在队列中合并扣减。
- 拆桶后“库存不足”可能只是当前桶不足：失败时再尝试其他桶，全部不足才返回售罄。

## 4. 测试清单

- 压测：请求数远大于库存，成交数等于库存，数据库库存不为负。
- 同一用户并发多次只成交一次。
- 数据库失败时 Redis 回补；Redis 清空后能从数据库重建。
