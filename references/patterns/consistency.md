# 一致性：幂等、事务、发件箱与补偿

适用：所有会产生后果的写操作，以及跨模块、跨系统的业务（下单 → 支付 → 发券 → 积分 → 通知）。
参考代码：`backend/00-framework/code/luzback/idempotency.py`、`outbox.py`、`statemachine.py`。
相关规范：ORDER-001、ORDER-002、ORDER-006、DATA-001、RESIL-002。

## 1. 幂等：同一意图只生效一次

| 手段 | 用在哪里 | 做法 |
|---|---|---|
| 幂等键 | 下单、支付、退款、领券、充值等用户发起的写请求 | 客户端每个意图生成一个 `Idempotency-Key`，重试沿用；服务端按“用户 + 操作 + 键”保存首次结果，同键不同请求体报 `IDEMPOTENCY_MISMATCH` |
| 唯一约束 | 回调、事件消费、流水 | 渠道交易号、退款单号、`ref + kind` 建唯一约束，重复写入被数据库拒绝 |
| 状态机条件更新 | 状态变化 | `WHERE status = 旧状态`，第二次执行影响 0 行 |
| 业务单号复用 | 退款、关单、发货 | 失败重试沿用原单号，渠道侧也按单号去重（RFD-002） |

只靠前端禁用按钮不是幂等。

## 2. 本地事务的边界

- 一个事务只写本系统数据库：业务数据、状态、流水、幂等记录、发件箱事件，一起提交或一起回滚。
- **事务里不调外部接口**（支付、短信、地图、模型）：外部调用慢且不可回滚，会拉长锁时间。
- 外部调用放在事务之前（例如先拿到 prepay_id 再保存）或之后（通过发件箱）。

## 3. 跨模块 / 跨系统：方案对比

| 方案 | 做法 | 一致性 | 复杂度 | 何时用 |
|---|---|---|---|---|
| **发件箱 / 本地消息表（默认）** | 业务写入与“待发布事件”同一事务提交；后台投递，消费者按事件 ID 幂等 | 最终一致 | 低 | 单体或少量服务；支付成功后的发券、积分、通知、履约 |
| 事务消息 | MQ 半消息 + 回查 | 最终一致 | 中，依赖 RocketMQ 等 | 已使用支持事务消息的 MQ |
| Saga | 每步有补偿动作，失败时反向补偿 | 最终一致 | 中 | 多服务长流程（下单 → 扣库存 → 扣余额 → 发券） |
| TCC | Try 预留 / Confirm 确认 / Cancel 取消 | 较强 | 高，每个参与方都要实现三阶段 | 资金类强一致、跨服务 |
| 两阶段提交 | 数据库 XA | 强 | 高，阻塞 | 一般不用于互联网业务 |

Luz 默认是单体加发件箱。库存预占本身就是一种 Try / Confirm / Cancel：预占对应 Try，确认对应 Confirm，释放对应 Cancel。

## 4. 发件箱要点

| 要点 | 做法 |
|---|---|
| 写入 | `enqueue_event(db, topic, payload)` 与业务写入同一事务 |
| 投递 | `OutboxWorker` 轮询未投递事件，至少一次投递 |
| 消费 | 消费者先检查 `ProcessedEvent`（事件 ID 唯一），处理与标记同一事务 |
| 失败 | 有界重试 + 退避；超过次数进死信，告警并提供人工重放 |
| 顺序 | 同一业务对象的事件带版本号；消费者丢弃旧版本 |

## 5. 补偿与对账

- 每个“已提交但后续失败”的情况都要有补偿：关单释放库存、支付成功但订单已取消则自动退款、发券失败重试。
- 每日对账兜底：支付对账（RFD-005）、库存流水对账、钱包流水对账；差异进人工队列，不自动“修平”。

## 6. 测试清单

- 同一请求并发 10 次只产生 1 条业务记录。
- 事务中途失败时，业务数据与发件箱事件都不存在。
- 消费者重复收到同一事件只处理一次。
- 外部依赖失败时重试有上限，降级不伪造成功。
