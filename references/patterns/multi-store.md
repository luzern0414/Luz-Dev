# 多门店与多租户数据隔离

相关：`backend/22-admin-rbac/MODULE.md`。相关规范：AUTHZ-001、AUTHZ-002、OBS-002。

## 1. 隔离方案

| 方案 | 做法 | 优点 | 缺点 | 何时用 |
|---|---|---|---|---|
| **共享表 + 租户 / 门店字段（默认）** | 每张业务表带 `tenant_id`、`store_id`，所有查询自动附加条件 | 成本低、易维护 | 一处遗漏即越权，必须统一拦截 | 单商户多门店、中小 SaaS |
| 每租户独立 Schema | 同库不同 Schema | 隔离较强 | 迁移与运维复杂 | 租户数量少、要求隔离 |
| 每租户独立数据库 | 独立库 | 隔离最强 | 成本高 | 大客户、合规要求 |

## 2. 规则

| 规则 | 做法 |
|---|---|
| 统一注入 | 在数据访问层统一附加租户 / 门店条件（ORM 查询过滤或仓储基类），不在每个接口手写 |
| 数据范围 | 角色的数据范围：全部 / 本门店 / 本人；后台账号可绑定多个门店 |
| 唯一约束 | 业务唯一约束包含租户字段（如租户 + 手机号） |
| 跨门店 | 会员、储值是否跨门店通用由商户决定，写入方案待决问题 |
| 报表 | 汇总按门店分组；总部视图需要“全部门店”权限 |
| 测试 | 每个接口都有“门店 A 的账号访问门店 B 数据”测试 |
