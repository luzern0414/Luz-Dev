# 缓存与一致性

原则：数据库是事实来源；缓存可以丢、可以重建。库存扣减、余额、订单状态这类必须准确的判断不以缓存为准（seckill.md 的 Redis 预扣只是前置过滤，数据库仍然兜底）。

## 1. 读写模式

| 模式 | 做法 | 结论 |
|---|---|---|
| **旁路缓存（默认）** | 读：缓存未命中查库并回填（带过期时间）；写：先更新数据库，再删除缓存 | 简单可靠 |
| 先删缓存再更新数据库 | — | 并发读会把旧值回填，**不用** |
| 更新数据库后更新缓存 | — | 并发写顺序错乱导致旧值覆盖新值，**不用** |
| 延迟双删 | 更新数据库 → 删缓存 → 延迟几百毫秒再删一次 | 主从延迟较大时补充使用 |
| 订阅数据库变更删除缓存 | binlog / CDC | 大规模时使用，删除失败可重试 |

删除失败要重试（或写发件箱异步删除），并且所有缓存都必须有过期时间作为最终兜底。

## 2. 三类问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 穿透 | 查询不存在的数据，每次都打到数据库 | 缓存空值（短过期）；参数校验；布隆过滤器 |
| 击穿 | 热点键过期瞬间大量请求打到数据库 | 互斥重建（只让一个请求回源）；热点键逻辑过期 |
| 雪崩 | 大量键同时过期或缓存宕机 | 过期时间加随机；多级缓存；限流降级 |

## 3. 适合缓存的数据

商品详情、分类、门店信息、配置、字典、排课表（短过期）。不适合：库存精确值、余额、订单状态、权限变更后的旧令牌。

## 4. 测试清单

- 更新后读取得到新值；并发读写下不出现长期旧值。
- 缓存不可用时系统降级到数据库并限流，不报错误数据。
