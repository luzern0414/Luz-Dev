# 库存与防超卖

适用：商品库存、课程 / 场地名额、券库存、抽奖奖品数量——凡是“有限数量被并发争抢”的资源。
参考代码：`backend/07-inventory/code/inventory/__init__.py`（条件扣减）、`inventory/reservation.py`（预占 / 确认 / 释放 / 流水），测试 13 项（含 50 并发、关单与支付竞态）。
相关规范：ORDER-003、ORDER-004、DATA-001、MONEY-004。

## 1. 库存模型

| 模型 | 字段 | 适用 | 说明 |
|---|---|---|---|
| 单字段（Luz 默认） | `stock` = 可售库存；预占记录在 `stock_reservations` | 门店、课程、中小电商 | 预占即扣减可售库存；实际在库 = 可售 + 未释放预占，可由预占表算出 |
| 双字段 | `available` 可售、`locked` 锁定（`on_hand = available + locked`） | 仓储、需要展示锁定量的后台 | 预占：available − n、locked + n；确认：locked − n；释放：反向 |
| 多仓 / 渠道 | 每个仓或渠道一行 | 多仓发货、线上线下共享库存 | 先选仓再扣减；跨仓调拨走调拨单 |

库存表只存当前值，所有变化另记**只追加的流水**（`stock_ledger`），当前值 = 初始 + Σ 流水，可随时对账。

## 2. 什么时候扣减

| 方式 | 做法 | 优点 | 风险 | 何时用 |
|---|---|---|---|---|
| 下单减库存 | 创建订单时扣，取消回补 | 不会出现“付了钱没货” | 恶意下单占库存 | 与预占搭配使用 |
| 支付减库存 | 支付成功时扣 | 不怕恶意占库存 | 付款成功后才发现没货，需要退款 | 库存充足、虚拟商品 |
| **预占（Luz 默认）** | 下单预占并设置过期时间（= 支付时限），支付成功确认，取消 / 超时释放 | 兼顾两者，过期自动归还 | 需要关单任务和竞态处理 | 绝大多数场景 |

预占过期时间必须与订单支付时限、微信下单的 `time_expire` 一致（PAY-002、ORDER-004）。

## 3. 防超卖：做法对比

| 做法 | 写法 | 结论 |
|---|---|---|
| 先查后改 | `SELECT stock` → 判断 → `UPDATE stock = :new` | **禁止**。两步之间会被并发请求插入 |
| **条件更新（默认）** | `UPDATE skus SET stock = stock - :n WHERE id = :id AND stock >= :n AND status = 'on_sale'`，影响行数 = 1 才成功 | 数据库裁决，多实例、任意并发都成立；性能足以覆盖普通门店与电商 |
| 乐观锁 | `WHERE version = :v`，失败重试 | 竞争大时重试风暴；适合低冲突的“读改写”复杂计算 |
| 悲观锁 | `SELECT … FOR UPDATE` | 持锁时间长，事务里不能有外部调用；仅在一次要读多行再决定时使用 |
| 应用内锁 / 单机锁 | `threading.Lock` | **禁止**。多实例部署即失效 |
| 分布式锁 | Redis `SET NX` | 只能降低冲突，不能代替数据库约束；锁过期、主从切换都会失效 |
| Redis 预扣（热点） | Lua 原子 `if stock >= n then decrby` | 秒杀、超热点 SKU 的前置过滤，数据库条件更新仍然兜底（见 seckill.md） |

## 4. 预占流程

```text
reserve(ref, {sku: qty}, ttl)      下单事务内：按 sku_id 升序逐个条件扣减 → 写预占（唯一 ref+sku）→ 写流水
confirm(ref)                       支付成功：reserved → confirmed（条件更新，幂等）
release(ref)                       取消 / 超时：reserved → released，回补库存，写流水（幂等，不重复回补）
release(ref, allow_confirmed=True) 已支付退款后回库（按退款回滚策略决定是否调用）
expired_refs(now)                  关单任务找出过期未确认的预占
```

状态机：`reserved → confirmed | released`，`confirmed → released`；`released` 为终态。

要点：

- **全有或全无**：多 SKU 订单任一不足，整个事务回滚，已扣的一起回滚。
- **固定加锁顺序**：按 `sku_id` 升序扣减，避免两个订单互相等待对方持有的行而死锁。
- **幂等**：同一业务单重复预占返回已有结果；数量不同则报 `IDEMPOTENCY_MISMATCH`。
- **事务里不调外部接口**：扣库存的事务里不调用支付、短信等外部服务。

## 5. 竞态与异常

| 情况 | 处理 |
|---|---|
| 关单任务释放时，支付回调刚好确认 | 释放用条件更新，失败后重读状态；已确认则抛 CONFLICT，关单任务按“已支付”处理，不回补（测试 `test_release_racing_with_confirm_reports_paid`） |
| 预占已超时释放，之后才收到支付成功 | `confirm` 返回 CONFLICT：重新尝试扣减；扣减失败则自动退款并告警（PAY-014 “关单后又收到 SUCCESS”） |
| 重复回调 / 重复取消 | 状态机条件更新只成功一次，流水唯一约束防重复记账 |
| 后台手工调整库存 | 走调整单：原因必填、写审计与流水；调整后可售库存不能小于 0 |
| 库存与流水不一致 | 每日对账：初始 + Σ 流水 = 当前库存；不一致告警，不自动修正 |

## 6. 测试清单

- 并发：N 个请求抢 M 件（N > M），成功数恰好 M，库存不为负。
- 多 SKU 订单任一不足时全部回滚。
- 重复预占、重复确认、重复释放均幂等。
- 超时释放后确认失败；释放与确认竞态。
- 流水累加与库存一致。
- 下架商品不能扣减。
