交付与验证 MUST 4 · SHOULD 1

PROC-001MUST正式页面只展示后端返回的真实数据全部 · 通用

正式业务页面的列表、统计、金额、状态和用户信息全部来自后端接口与数据库；不得写死业务数据、伪造成功状态或用模拟数据掩盖接口缺失。

原因：模拟数据会让未完成的链路看起来可用，上线后才暴露数据不一致。

做法

  • 测试数据只放在隔离环境，可识别、可清理
  • 接口缺失时页面显示明确的不可用状态

禁止

  • 在页面里写死示例订单或统计
  • 接口失败时显示假的成功提示

验证方式

  • 刷新、重新登录、换设备后页面与数据库一致
  • 代码检索没有正式页面引用 mock 数据

依据

  • 开发规范 · 三、1 真实数据驱动
PROC-002MUST区分已编写、已运行、已测试通过、已上线验证全部 · 通用

交付报告与方案核对表必须区分四种状态；没有真实执行的功能不得标记为测试通过，无法访问的环境写明验证范围与未完成事项。

原因：把“写完了”说成“验证过”是交付事故最常见的来源。

做法

  • 交付记录每项附验证命令、结果与时间
  • 无法验证的内容列为遗留事项

禁止

  • 用“应该可以”代替实际测试
  • 只凭单元测试宣称端到端可用

验证方式

  • tech_plan.py check --stage delivery 通过
  • 每条 done 记录都有证据

依据

  • 开发规范 · 九、逐项测试与真实验收
PROC-003MUST每个功能逐项走通真实链路全部 · 通用

每个功能依次验证：进入页面、请求接口、后端校验身份与权限、读写数据库、返回结果、前端展示最新结果、刷新或重新登录后持久化、异常时给出可恢复提示。

原因：页面能打开不代表业务能完成；前后端各自正确也可能拼接出错。

做法

  • 每个按钮都有真实接口与结果反馈
  • 检查数据库实际变化

禁止

  • 只验证接口返回 200
  • 保留没有功能的按钮或空链接

验证方式

  • 端到端用例覆盖核心流程
  • 测试记录包含数据库核对

依据

  • 开发规范 · 五、前后端及小程序完整打通
PROC-004MUST交付 /config 与 README全部 · 通用

验收后在项目根目录 /config 记录各环境配置项、用途、获取方式与验证方法，并更新 README（简介、技术栈、目录、启动、迁移、联调、测试、部署、排障、遗留问题）；秘密只记录位置不记录值。

原因：没有配置与运行文档的系统无法交接和运维。

做法

  • 开发、测试、生产配置分开
  • 提供带必填项检查的配置模板

禁止

  • 把真实密码、私钥、令牌写进仓库或文档
  • 记录未经验证的地址

验证方式

  • 新成员按 README 能从零启动
  • 仓库秘密扫描无命中

依据

  • 开发规范 · 十一、配置、安全与文档交付
PROC-005SHOULD引入依赖前评估许可证、维护度与安全全部 · 通用

新依赖或外部服务说明选择原因、替代方案、许可证、维护活跃度和已知漏洞；网上示例代码不能直接作为生产代码。

做法

认证与会话 MUST 5 · SHOULD 1

AUTH-001MUST接口默认需要认证，公开接口逐个登记后端服务 · 通用

所有接口默认要求有效的登录凭证；不需要登录的接口（健康检查、渠道回调、公开内容）在路由层显式登记并单独评审。

原因：默认放行会让新增接口意外暴露。

做法

  • 在框架层统一注入认证依赖
  • 公开接口清单写入方案的接口表

禁止

  • 在每个处理函数里各自手写鉴权

验证方式

  • 自动化测试遍历路由，未登记的路由无凭证访问返回 401

  • OWASP Authorization Cheat Sheet · Deny by default
AUTH-002MUST访问令牌短时有效，可撤销后端服务 · 通用

访问令牌有明确过期时间；刷新令牌可撤销并轮换；登出、改密、封禁后旧令牌立即失效。

原因：长期有效且不可撤销的令牌一旦泄露无法止损。

做法

  • 访问令牌短时效 + 刷新令牌轮换
  • 服务端保存令牌版本或会话记录用于撤销

禁止

  • 把令牌放在 URL 参数中
  • 签发不过期的令牌

验证方式

  • 登出或改密后旧令牌请求返回 401

依据

  • OWASP Session Management Cheat Sheet
AUTH-003MUST小程序登录在服务端换取身份，session_key 不下发小程序、后端服务 · login

小程序端只把 wx.login 得到的 code 交给后端；后端调用 code2Session 换取 openid / unionid / session_key，session_key 只保存在服务端，不返回给前端、不写入日志、不作为业务登录凭证；后端签发自己的登录令牌。

原因：session_key 是解密用户数据的密钥，泄露后可伪造或解密用户信息。

做法

  • 后端签发自有令牌并绑定 openid
  • code 只使用一次

禁止

  • 在小程序里调用 code2Session 或保存 AppSecret
  • 把 openid 直接当作登录凭证

验证方式

  • 前端包与接口响应中检索不到 session_key 与 AppSecret

依据

  • 微信开放文档 · 小程序登录
  • 微信开放文档 · code2Session
AUTH-004MUSTaccess_token 由服务端统一获取和缓存后端服务 · login

调用微信服务端接口所需的 access_token 由一个中控服务获取、缓存并在过期前刷新；多个实例共用同一份，不在各处分别刷新。

原因：多处刷新会让彼此的令牌失效，导致接口间歇失败。

做法

  • 优先使用稳定版接口调用凭据
  • 缓存时记录过期时间并提前刷新

禁止

  • 每次调用前都重新获取 access_token
  • 把 access_token 下发到前端

验证方式

  • 并发多实例压测期间不出现 access_token 失效错误

依据

  • 微信开放文档 · getStableAccessToken
AUTH-005MUST后台密码安全存储与失败锁定管理后台、后端服务 · 通用

后台账号密码用 Argon2id 或 bcrypt 等慢摘要加盐存储；连续失败按账号和来源限速并锁定（界面设计 Admin 规范：5 次失败锁 15 分钟）；初始密码首次登录强制修改。

原因：弱存储与无限重试是后台被撞库的主要原因。

做法

  • 锁定提示显示剩余时间
  • 重置密码走一次性链接或验证码

禁止

  • 明文或可逆加密存储密码
  • 错误提示区分“账号不存在”和“密码错误”

验证方式

  • 连续 5 次错误后第 6 次被拒绝且有审计记录
  • 数据库中只有密码摘要

依据

  • OWASP Password Storage Cheat Sheet
  • 界面设计 · 管理后台规范 §10 状态（锁定）
AUTH-006SHOULD高权限账号启用二次验证与会话超时管理后台、后端服务 · 通用

超级管理员、财务、退款审批等高权限角色启用二次验证；后台会话无操作超时（Admin 规范为 2 小时，提前 5 分钟提醒）。

原因：高权限账号被盗的损失远大于普通账号。

做法

  • 敏感操作前重新验证身份

禁止

  • 让高权限账号长期保持登录

验证方式

  • 超时后请求返回 401 并保留未保存草稿

依据

  • 界面设计 · 管理后台规范 §10、§15

授权与数据隔离 MUST 4 · SHOULD 0

AUTHZ-001MUST服务端校验资源归属，防止越权访问后端服务 · 通用

按 ID 读取或修改资源时，在查询条件中同时限定当前用户、门店或租户（例如 WHERE id = ? AND user_id = ?）；不存在与无权访问统一返回 404 或 403，不泄露对象是否存在。

原因：越权访问（IDOR）是业务系统最常见的漏洞：换一个订单号就能看到别人的订单。

做法

  • 列表、详情、导出、统计全部带数据范围条件
  • 测试用另一个账号访问同一资源

禁止

  • 只靠前端隐藏按钮控制权限
  • 先按 ID 查出再在内存里判断归属却忘记某个分支

验证方式

  • 每个按 ID 访问的接口都有跨账号访问测试且返回 403/404

依据

  • OWASP Authorization Cheat Sheet · IDOR
AUTHZ-002MUST后台权限精确到接口与数据范围管理后台、后端服务 · 通用

后台权限码同时控制菜单、按钮和后端接口；后端每个接口校验权限码，并按角色的数据范围（全部 / 本门店 / 本人）过滤数据。

原因：只控制菜单的权限可以被直接调接口绕过。

做法

  • 权限码与 backend/22-admin-rbac 保持一致
  • 权限变更写审计

禁止

  • 用角色名硬编码判断权限

验证方式

  • 无权限账号直接调用接口返回 403
  • 门店 A 的管理员查不到门店 B 的数据

依据

  • Luz Dev · backend/22-admin-rbac/MODULE.md
AUTHZ-003MUST批量赋值只接受白名单字段后端服务 · 通用

创建和更新接口用显式的输入模型，只接受允许用户修改的字段；状态、金额、归属、角色等字段只能由服务端设置。

原因：把请求体整体写进数据库会让用户改掉价格、状态或角色。

做法

  • 为创建、更新、管理员更新分别定义输入模型

禁止

  • model.update(**request.json())

验证方式

  • 提交额外的 status/amount/role 字段不生效

依据

  • OWASP Mass Assignment Cheat Sheet
AUTHZ-004MUST多门店 / 多租户条件在数据访问层统一注入后端服务、管理后台 · store

每张业务表带租户 / 门店字段，查询在数据访问层统一附加数据范围条件，不在每个接口手写；业务唯一约束包含租户字段；会员、储值是否跨门店通用由商户决定并写入方案。

原因：手写条件只要漏一处就会让门店看到其他门店的会员与订单。

做法

  • 每个接口都有跨门店访问测试

禁止

  • 只在前端按门店过滤

验证方式

  • 门店 A 账号访问门店 B 数据返回 403/404

依据

  • Luz Dev 模式库 · 多门店隔离

输入、输出与错误 MUST 4 · SHOULD 0

INPUT-001MUST所有输入按模型校验类型、长度与范围后端服务 · 通用

路径、查询、请求体、请求头和回调数据都通过 schema 校验类型、必填、长度、范围和枚举；分页大小设上限；校验失败返回稳定错误码和字段级信息。

原因：未约束的输入会导致注入、超大请求、越界和脏数据。

做法

  • 前后端使用同一份校验规则
  • 请求体大小设上限

禁止

  • 信任前端已校验
  • 允许 page_size 任意大

验证方式

  • 边界值与非法值测试返回 4xx 且数据库无变化

依据

  • OWASP Input Validation Cheat Sheet
INPUT-002MUST数据库访问一律参数化后端服务 · 通用

SQL 通过 ORM 或参数绑定执行；排序字段、表名等无法参数化的部分用白名单映射。

原因：字符串拼接 SQL 是注入漏洞的直接来源。

做法

  • 排序参数映射到固定列名

禁止

  • f"SELECT ... WHERE name = '{name}'"

验证方式

  • 代码检索无 SQL 字符串拼接
  • 注入载荷测试无异常

依据

  • OWASP SQL Injection Prevention Cheat Sheet
INPUT-003MUST错误响应不暴露内部信息后端服务、管理后台、小程序、移动 App · 通用

错误统一为信封格式：稳定的 code、面向用户的 message、trace_id；不返回堆栈、SQL、内部地址、密钥或第三方原始报错。

原因：内部报错既泄露攻击面，也让用户看不懂。

做法

  • 前端按错误码映射用户文案与下一步动作
  • 500 页面提供可复制的 trace_id

禁止

  • 把异常 str(e) 直接返回给前端

验证方式

  • 故意触发异常，响应中无堆栈与内部字段

依据

  • Luz Dev · backend/SPEC.md 错误信封
INPUT-004MUST富文本与用户内容输出前转义或净化管理后台、小程序、移动 App · 通用

用户提交的文本按纯文本渲染；确需富文本时用白名单净化库处理；后台渲染用户内容同样转义。

原因：存储型 XSS 往往在后台被管理员触发，危害最大。

做法

  • 使用框架默认的文本绑定
  • 富文本用白名单标签和属性

禁止

  • v-html / rich-text 直接渲染用户输入

验证方式

  • 提交 <script> 与事件属性载荷，前台与后台均不执行

依据

  • OWASP Cross Site Scripting Prevention Cheat Sheet

金额与资金 MUST 4 · SHOULD 0

MONEY-001MUST金额以整数“分”存储和计算后端服务、管理后台、小程序、移动 App · 通用

金额字段使用整数最小货币单位（分），计算、传输、比较都用整数；只在展示时格式化为元。

原因：浮点数会产生 0.1 + 0.2 ≠ 0.3 之类的误差，对账对不上。微信支付金额同样以分为单位。

做法

  • 字段命名带 _cents 或 _fen
  • 前端展示统一格式化函数

禁止

  • 用 float/double 存金额
  • 前端计算应付金额并提交给后端

验证方式

  • 金额字段类型为整数
  • 折扣与分摊的边界用例结果为整数且合计一致

依据

  • 微信支付 · JSAPI下单 amount.total（单位为分）
MONEY-002MUST应付金额只由服务端计算后端服务 · 通用

订单应付金额由服务端根据商品价格快照、优惠规则、运费等计算；前端传来的金额只用于提示比对，不参与计费。

原因：信任前端金额等于允许用户自己定价。

做法

  • 下单时保存价格与优惠快照
  • 前后端金额不一致时返回价格已变化

禁止

  • 使用请求中的 total_amount 发起支付

验证方式

  • 篡改请求金额的测试中支付金额不变

依据

  • Luz Dev · backend/09-wechat-pay/MODULE.md §1 步骤 2
MONEY-003MUST优惠分摊有确定的余数规则后端服务 · 通用

整单优惠按明细比例分摊到每一行，四舍五入产生的余数按固定规则（例如归最后一行）处理，保证明细合计等于整单金额；部分退款按分摊后的行金额计算。

原因：没有分摊规则时，部分退款会多退或少退。

做法

  • 分摊结果写入订单明细快照
  • 为 1 分钱、多行、全额优惠写测试

禁止

  • 退款时重新计算优惠

验证方式

  • 任意组合下明细合计 = 实付；累计退款不超过实付

依据

  • 内部经验规则
MONEY-004MUST资金变动有不可变流水后端服务 · 通用

余额、积分、储值、退款等任何资金类变动都写入只追加的流水（变动前、变动额、变动后、业务单号、操作人、时间），余额由流水可重算。

原因：只有最终余额而没有流水时，出现差异无法追查。

做法

  • 流水表对业务单号 + 类型建唯一约束防重复

禁止

  • 直接 UPDATE 余额而不记流水
  • 修改或删除历史流水

验证方式

  • 抽样账户：流水累加 = 当前余额

依据

订单、库存与状态机 MUST 10 · SHOULD 0

ORDER-001MUST状态流转用条件更新守卫后端服务 · order、payment、refund、coupon、reservation、membership、recharge

订单、支付单、退款单、券等状态变化用 UPDATE ... WHERE status = 原状态 执行，影响行数为 0 时返回稳定错误，不覆盖更新的状态；状态机在方案中列出全部合法流转。

原因：并发请求或延迟回调会把已完成的订单改回旧状态。

做法

  • 方案中写状态 | 触发 | 守卫 | 副作用表
  • 非法流转返回 409 与稳定错误码

禁止

  • 先查状态再无条件更新

验证方式

  • 并发与乱序测试中状态只按合法路径前进

依据

  • Luz Dev · backend/SPEC.md 状态机
ORDER-002MUST会产生后果的写请求支持幂等后端服务、小程序、移动 App、管理后台 · 通用

下单、支付、退款、领券、核销、充值等写请求带 Idempotency-Key；服务端按“用户 + 操作 + 键”保存首次结果，重复请求返回同一结果；回调按渠道事件或业务单号幂等。

原因：网络重试、双击和回调重发都会造成重复下单、重复扣款。

做法

  • 前端每次用户意图生成一个键，重试沿用
  • 幂等记录与业务写入同一事务

禁止

  • 只靠前端禁用按钮防重复

验证方式

  • 同一键并发提交 10 次只产生 1 条业务记录

依据

REL-003MUST小程序与 App 的代码更新：提示重启、最低可用版本、热更新边界小程序、移动 App · deploy

小程序用 wx.getUpdateManager 在新版本下载完成时提示重启，用户确认后 applyUpdate，不在填写或支付中打断；必须修复的问题在微信后台设最低可用版本。App 启动检查最新与最低可用版本，低于最低版本时引导更新；热更新只更新资源与配置，不下载执行会新增或改变功能的代码。

原因：小程序新版本默认要等下次冷启动才生效，旧版本可能长期在用；App 下载执行改变功能的代码违反苹果审核指南 2.5.2。

做法

  • 更新提示写清更新了什么
  • 最低可用版本与后端接口兼容性一起评估

禁止

  • 用热更新上线未经审核的新功能

验证方式

  • 发布新版本后旧客户端出现重启提示且不打断支付
  • 低于最低版本的客户端被引导更新

依据
